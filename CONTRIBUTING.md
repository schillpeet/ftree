# Contributing to ftree

Thanks for helping! This guide covers how to get the project running and how changes reach `main`.

## Get started

```bash
git clone git@github.com:schillpeet/ftree.git
cd ftree
./setup.sh      # checks Node, pnpm, Docker, Java and tells you how to install what is missing
./start.sh      # PostgreSQL, Swagger UI, backend, UI
```

Open [http://localhost:3000](http://localhost:3000). The [README](README.md) explains the layout and the individual commands, and [`docs/project-overview.md`](docs/project-overview.md) describes what is implemented and what is planned.
Read the overview before changing product behavior, data, or architecture, and keep it accurate when you do.

## Branches and commits

1. Never commit to `main`. Start from the latest `main`:

   ```bash
   git fetch origin
   git switch -c <type>/<scope>-<message-in-kebab-case> origin/main
   ```

   For example `feat/ui-add-person-detail-panel`.

2. Write commit messages as `<type>(<scope>): <message>`, entirely lowercase, in English, in the imperative mood, for example `feat(ui): add person detail panel`. `./setup.sh` enables the `.githooks/commit-msg` hook that rejects other messages, and the PR-title workflow checks the title and every commit of a pull request with the same script.

   | Type       | Use for                                                    |
   | ---------- | ---------------------------------------------------------- |
   | `feat`     | new user-facing or developer-facing functionality          |
   | `fix`      | bug fixes                                                  |
   | `docs`     | documentation-only changes                                 |
   | `refactor` | code restructuring without behavior changes                |
   | `test`     | adding or changing tests                                   |
   | `chore`    | maintenance that adds no functionality                     |
   | `build`    | build system or external dependency changes                |
   | `ci`       | CI configuration changes                                   |
   | `deps`     | dependency updates, reserved for Dependabot                |

   Scopes are `ui`, `bff`, `db`, and `repo`. Mark breaking changes with `!`, for example `feat(bff)!: rename member fields`.
   Choose the type by meaning: anything that introduces new functionality is `feat`, even if it only touches scripts or configuration.

3. Do not edit generated API code. Change [`api/openapi.yaml`](api/openapi.yaml) and regenerate (`(cd ui && pnpm api:generate)`; the backend regenerates on build).

4. Family relationships and identifying information are sensitive. Do not assume public access, and define authorization and sharing rules before implementing anything that shares data.

## Check your change

Run what CI runs before you push. Run pnpm from inside `ui/`: only there it switches to the pnpm version pinned in `ui/package.json`, while `pnpm --dir ui` would use whatever version is installed globally.

```bash
(cd ui && pnpm lint && pnpm typecheck && pnpm build)
(cd bff && ./gradlew build)         # needs the database running (./start.sh)
```

Then bring your branch up to date and re-run the checks if anything came in:

```bash
git fetch origin && git rebase origin/main
```

## Open a pull request

1. Push your branch to this repository (collaborators) or to your fork.
2. Open a pull request against `main`. The PR title uses the same lowercase `<type>(<scope>): <message>` format; the `validate` check fails otherwise.
3. Wait for the required checks (`validate`, `ci-ok`) to pass.
4. The branch rules require one approval from a maintainer before a pull request can be merged, and a new push after the approval needs a new approval.

Release notes and version bumps are generated by release-please from the commit types. Never set versions or create tags by hand.
Pull requests are squash-merged. One that contains several independently releasable features or fixes lists them in its description, one Conventional Commit line each, so every change gets its own changelog entry:

```
BEGIN_COMMIT_OVERRIDE
fix(bff): bound gedcom import memory (#259)
feat(ui): add empty tree onboarding and feedback link (#259)
END_COMMIT_OVERRIDE
```

## Reporting problems

Open an issue with what you did, what you expected, and what happened. Do not post real family data; use the fictional demo family in [`docs/preview/demo.ged`](docs/preview/demo.ged) instead.
